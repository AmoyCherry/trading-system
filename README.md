# trading-system

## What's this?

This is a performance measurement harness to quantify and attribute C++ features regarding latency and perf counters.

Three single-threaded processes in this project: _exchange_sim_, _gateway_, _lobd_ (lob daemon). Their functionalities are shown in the figure below.

![overview](./assets/overview.jpg)

> Gray text with arrows are instrumented code.
> - `before/after_* →`: timestamp by `clock_gettime(CLOCK_MONOTONIC_RAW)`
> - `getrusage`: fetch voluntary and invol ctx switches.

**Measurement Validity** is the first-class citizen:
- reproducibility;
- positive/negative controls;
- single-variable and hypothesis frist experiments.
- stat validity:
  - p50/p99 latency;
  - center±spread (med±robust CV) report;
  - gated by `MDE=k·MAD`;
- credible baseline:
  - [w2w bottleneck](./docs/experiments/w2w_ex2gw_bottleneck/w2w_bottleneck_saturation.md)
  - [os preemption](./docs/experiments/os-preemption/negative_latencies.md)

### Workflow

Select a baseline version → change a single variable → make a hypothesis → experiment.

Two kinds of experiments can be run to get latency or perf counters, for each variable:
- latency experiment: To stat latencies for every interval. All timestamps will be collected for every msg.
- perf experiment: To attribute perf counters to matching engine. All timestamps will be disabled to remove clock noise. 

Every kind of expr have several repeats (default 10). Every repeat run needs to confirm a data scenario `[add, cross, cancel]` and a running mode `[null, decode, match]`. Latency experiment needs to run `[add, cross, cancel]` × `[match]`, the complete `lobd`. While perf experiment needs to run a matrix `[add, cross, cancel]` × `[null, decode, match]`, then use cross-mode delta to attribute the perf counters to the matching engine.

## Technical Detail for Measurement Validity

Reproducibility is guaranteed by 
- two determinism oracles:
  - Msg hash. Rolling hash for every bit of every msg generated by `ex`. Comparing latency/perf difference with the baseline should assert their msg hashes are identical.
  - Book state hash. Different experiments should have bit-exact states (identical state hashes) in `lobd` when everything done. 
- controlled variables
  - CPU pinning. All three processes are pinned to different p-core (by `taskset -c` or in binary `sched_setaffinity`).
  - CPU governor. Set `scaling_governor` to `performance` + enable `turbo-off`. Thus, to limit CPU frequency into a narrowband.
  - `isolcpu`. Still disabled. But now I indeed need it due to a solid evidence ([negative intervals](./docs/experiments/os-preemption/negative_latencies.md)). 
  - pre-faulting.

Negative Controls: unmodified intervals' latency stats should keep unchanged compared with baseline.


## What is trading?

There are some instruments and assets, like stocks, futures and cryptos.

People buy and sell these items from each other via the exchange. All bid orders and ask orders are sent to the exchange process.

- The Best Bid is the highest price that buyers are willing to buy.
- The Best Ask is the lowest price that sellers are willing to sell.

When `Best Bid >= Best Ask`, the orders can be matched.

The exchange receives those orders from both sides in the same queue sequentially. It processes one order at a time. If `Best Bid >= Best Ask`, it will match the orders exhaustedly. All unmatched orders remain in the exchange to be maintained, called as Limit Order Book. For each item in the LOB, there is  `Best Bid < Best Ask`.

The exchange broadcasts order updates to subscribers, including those quant shops. They receive updates and reconstruct the LOB on their local, and run their algos to send orders to the exchange.
